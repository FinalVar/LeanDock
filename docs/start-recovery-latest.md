- 成功后取消定时器。查询已活动状态在尝试门限之前，能认领迟到完成。
- 一分钟内最多三次尝试；耗尽后不能由定时器自己重新开放预算，仅后续
  CREATE／SHOW／UNCLOAKED 等原生事件可重新开放。
- 停止／宿主退出取消定时器，旧排队定时回调不能取消新宿主尚未到期的重试。
- Start 记录初始化阶段、HRESULT 和独立失败次数；部分事件订阅分别还原。
  历史初始化失败不会直接污染布局运行失败计数。

#### 根因和状态解释

00:51:20 Explorer 换为 PID 25744，00:51:22 Start 换为 PID 30456。旧 Start 状态
文件仍指向已经退出的 PID 9728，而新进程没有加载紧凑布局 DLL。

旧控制器的 LeanDockStart::Attach 在发现所持有的 Start 进程句柄已退出时，
无条件设置 blocked=true 并停止重接。它没有读取退出码，也没有区分正常回收
与实际崩溃。因此本次 startLayoutBlocked 是自身的生命周期保护，不能仅根据
该字段称为 Windows 安全拦截。此前 2026-10-11 15:30 的 Code Integrity 拒绝是
另一个有时间戳的事件，不能拿它代替本次原因。

本次没有读取旧 Start 的退出码，因此不声称已经证明它以 0 退出；可确认的是
控制器对所有旧宿主退出都采用了同一停止分支。

独立重接保持原控制器为组件所有者，原 DLL 自身继续监控该所有者的进程句柄。
原控制器内的 blocked、target 状态没有被修改：其汇总仍可能显示 Start 不活动，
而当前宿主的属性、实际模块及 start/latest-status.json 已证实组件运行。
必须保留这一区别，不能手改控制器状态文件把它伪装成自动恢复就绪。

#### 复用与源码修正

开始菜单复用 include/quick-lifecycle-latest.h 中现有的 RestartPolicy，未另写
一套重试算法。只有通过原进程句柄确认退出码为 0 时，才允许在 60 秒内最多两次
重接；异常退出、未知退出码或超出次数仍停止，防止启动／崩溃循环。

旧句柄释放后同时清除旧窗口、旧尝试 PID 和活动状态。若原宿主仍存活，不把它
的句柄拿来配合另一个进程的窗口。停止组件时清理恢复计数与退出码记录。
仍使用已有的 CREATE／SHOW／UNCLOAKED 事件、原始固定哈希、线程专属 Windows
Hook 和原 DLL；没有新增常驻进程或周期扫描。

控制器状态增加恢复次数、最近退出码和退出码是否已知，便于以后区分正常回收、
崩溃、重复退出和系统镜像加载失败。
